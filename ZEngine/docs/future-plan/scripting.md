# ZEngine — Scripting and Game Logic Layer

**Priority:** P1 — Required for game logic iteration without full engine rebuilds
**Status:** Design
**Depends on:** `actor-ecs-architecture.md`, `system-scheduler.md`
**Blocks:** Game-specific behavior, NPC AI, gameplay systems
**Approach:** C++ DLL hot-reload via platform dlopen/LoadLibrary (v1); Lua scripting (v2)

---

## 1. Design Philosophy

Game-specific logic changes frequently during development. Recompiling the full engine to
test a change in player jump height or NPC patrol radius wastes minutes per iteration.
The standard solution is scripting; but scripting languages add runtime cost, binding
boilerplate, and a second language for the programmer to maintain.

ZEngine v1 takes a middle path: **game logic lives in a separate shared library** that the
engine loads and can reload at runtime without restarting. The game DLL is compiled C++,
which means:

- Zero overhead: game systems call engine APIs at full C++ speed, no marshalling.
- Full language support: templates, constexpr, the full standard library, ASAN/UBSAN.
- Familiar tooling: same compiler, debugger, and build system as the engine.
- Hot-reload: the DLL can be rebuilt and reloaded while the engine continues running;
  ECS component data survives the reload because it lives in the engine, not the DLL.

The boundary between engine and game is a **C ABI** (`extern "C"` entry points). A C ABI
is used — not C++ — because:

- C++ ABI is not stable across compiler versions, STL builds, or even translation units
  with different compilation flags.
- `dlopen` / `LoadLibrary` resolve symbols by name. C++ name mangling is compiler-specific.
- The C ABI contract is simple enough to write by hand and stable enough to never change.

The engine does not know the game's class hierarchy, includes, or namespaces. It only knows
the four `ZGame_*` entry points and the `ZGameContext` struct.

**What this is not:** this is not a scripting system in the sense of Lua, Python, or
C#. It is a compiled-code hot-reload system. Lua scripting is v2 (Section 7).

## 2. Game DLL Interface

The contract between engine and game DLL is defined in a single shared header that both
sides include.

```cpp
// ZEngine/Scripting/GameAPI.h
// Shared between the engine (consumer) and the game DLL (producer).
// Include in both. Do NOT include engine-internal headers here.
#pragma once
#include <cstdint>

// Increment this whenever ZGameContext layout changes.
#define ZGAME_CONTEXT_VERSION 1u

// Forward declarations — the game DLL receives pointers; it does not need full types
// unless it accesses members (in which case it includes the relevant engine header).
namespace ZEngine::ECS       { class Scene;               }
namespace ZEngine::ECS       { class WorldTick;           }
namespace ZEngine::ECS       { class ActorManager;        }
namespace ZEngine::Audio     { class AudioEngine;         }
namespace ZEngine::VFS       { class IVFSContext;         }
namespace ZEngine::Physics   { class PhysicsWorld;        }
namespace ZEngine::Animation { class AnimationManager;    }
namespace ZEngine::Input     { class InputManager;        }
namespace ZEngine::Network   { class NetworkSession;      }
namespace ZEngine::Rendering { class RenderResourceManager; }

namespace ZEngine::Scripting {

    /// All engine subsystems the game DLL may call.
    /// Populated by the engine before calling ZGame_Initialize.
    /// All pointers are valid for the lifetime of the game session.
    struct ZGameContext {
        // Version of ZGameContext layout. Validated by GameDLLLoader::Load().
        // Increment ZGAME_CONTEXT_VERSION whenever fields are added or reordered.
        // Old DLLs compiled against a different version are rejected at load time.
        uint32_t ContextVersion = ZGAME_CONTEXT_VERSION;

        // Engine version (set by Engine at runtime)
        uint32_t EngineMajor;
        uint32_t EngineMinor;
        // ... existing fields follow ...

        ECS::Scene*                        Scene;
        ECS::WorldTick*                    WorldTick;
        ECS::ActorManager*                 ActorManager;
        Audio::AudioEngine*                Audio;
        VFS::IVFSContext*                  VFS;
        Physics::PhysicsWorld*             Physics;
        Animation::AnimationManager*       Animation;
        Input::InputManager*               Input;
        Network::NetworkSession*           Network;    // null in single-player builds
        Rendering::RenderResourceManager*  RRM;

        // Engine version fields — used to detect stale game DLL after engine rebuild.
        // GAME_ENGINE_VERSION_MAJOR/MINOR are defined in EngineVersion.h, which is
        // generated by configure_file() at CMake configure time from the engine version.
        // Including EngineVersion.h in game_api.h ensures the check uses the version
        // at DLL build time, not a hardcoded constant.
        //
        //   #include <EngineVersion.h>   // in game_api.h
        //
        // The runtime check in ZGame_Initialize:
        //   ZENGINE_VALIDATE_ASSERT(
        //       ctx->EngineVersionMajor == ZENGINE_VERSION_MAJOR &&
        //       ctx->EngineVersionMinor == ZENGINE_VERSION_MINOR,
        //       "Game DLL was built against a different engine version. Rebuild the game.");
        uint32_t EngineVersionMajor;
        uint32_t EngineVersionMinor;
    };

}  // namespace ZEngine::Scripting

// C ABI entry points
// The game DLL must export all four. The engine resolves them by name via dlsym/GetProcAddress.
// No C++ name mangling: extern "C" is mandatory.

extern "C" {

    /// Called once after the DLL is loaded and all engine systems are initialized.
    /// The game registers its Actor factories here (see Section 5).
    /// ctx is valid for the entire game session (not just initialization).
    void ZGame_Initialize(ZEngine::Scripting::ZGameContext* ctx);

    /// Called before the DLL is unloaded.
    /// The game must release any resources it owns (audio handles, etc.).
    /// ECS component data must NOT be freed here — it belongs to the engine.
    void ZGame_Shutdown();

    /// Called once per (re-)load, after ZGame_Initialize.
    /// The game registers all ECS systems into WorldTick.
    /// On hot-reload this is called after WorldTick::BeginRebuild() and before Commit().
    void ZGame_RegisterSystems(ZEngine::ECS::WorldTick* world,
                               ZEngine::ECS::Scene*     scene);

    /// Called when a new scene finishes loading.
    /// The game spawns initial actors, reads scene-specific configuration, etc.
    void ZGame_OnSceneLoad(ZEngine::ECS::Scene* scene);

}
```

**Design notes:**

- The four entry points are the only mandatory symbols the engine resolves. The game DLL
  may export additional symbols for editor tooling, but the engine never calls them.
- `ZGameContext` is a plain struct with only pointers. It is safe to copy by value.
  The engine keeps a permanent instance on the stack of `GameDLLLoader::Load` and passes
  its address.
- `EngineVersionMajor` / `EngineVersionMinor` allow the game DLL to assert compatibility:
  ```cpp
  void ZGame_Initialize(ZGameContext* ctx) {
      ZENGINE_VALIDATE_ASSERT(ctx->EngineVersionMajor == GAME_ENGINE_VERSION_MAJOR,
                              "Engine major version mismatch — rebuild the game DLL")
      // ...
  }
  ```
- The game DLL must not call engine APIs from a DLL constructor (`DllMain` on Windows,
  `__attribute__((constructor))` on POSIX). The engine is not fully initialized at that
  point. Use `ZGame_Initialize`.

## 3. DLL Loader

```cpp
// ZEngine/Scripting/GameDLLLoader.h
#pragma once
#include <Scripting/GameAPI.h>
#include <Core/Memory/ArenaAllocator.h>

#if defined(_WIN32)
#  define WIN32_LEAN_AND_MEAN
#  include <windows.h>
   using DLHandle = HMODULE;
#else
   using DLHandle = void*;
#endif

namespace ZEngine::Scripting {

    /// Function pointer typedefs — resolved once per load.
    using ZGame_Initialize_Fn       = void (*)(ZGameContext*);
    using ZGame_Shutdown_Fn         = void (*)();
    using ZGame_RegisterSystems_Fn  = void (*)(ECS::WorldTick*, ECS::Scene*);
    using ZGame_OnSceneLoad_Fn      = void (*)(ECS::Scene*);

    struct GameDLLFunctions {
        ZGame_Initialize_Fn      Initialize      = nullptr;
        ZGame_Shutdown_Fn        Shutdown        = nullptr;
        ZGame_RegisterSystems_Fn RegisterSystems = nullptr;
        ZGame_OnSceneLoad_Fn     OnSceneLoad     = nullptr;
    };

    class GameDLLLoader {
    public:
        GameDLLLoader() = default;
        ~GameDLLLoader();

        GameDLLLoader(const GameDLLLoader&)            = delete;
        GameDLLLoader& operator=(const GameDLLLoader&) = delete;

        /// Load the game DLL from path. Resolves all ZGame_* symbols.
        /// Returns true on success. Logs and returns false on any failure.
        bool Load(const char* dll_path, ZGameContext* ctx);

        /// Call ZGame_Shutdown and unload the DLL.
        void Unload();

        /// Hot-reload: build a new version, call Reload, continue running.
        /// Steps:
        ///   1. Copy dll_path to a temp path (avoids Windows file lock).
        ///   2. dlopen/LoadLibrary the temp copy.
        ///   3. Resolve ZGame_* symbols from the new copy.
        ///   4. Call WorldTick::BeginRebuild() on the scheduler.
        ///   5. Call old ZGame_Shutdown().
        ///   6. dlclose/FreeLibrary the old handle.
        ///   7. Swap handles and function pointers.
        ///   8. Call new ZGame_Initialize(ctx).
        ///   9. Call new ZGame_RegisterSystems(world, scene).
        ///   10. Call WorldTick::Commit().
        ///
        /// Returns true if the reload succeeded. On failure, the old DLL remains active.
        bool Reload(const char*      dll_path,
                    ZGameContext*    ctx,
                    ECS::WorldTick*  world,
                    ECS::Scene*      scene);

        /// Returns true if a DLL is currently loaded.
        bool IsLoaded() const { return m_handle != nullptr; }

        /// Access resolved function pointers.
        const GameDLLFunctions& Functions() const { return m_funcs; }

    private:
        /// Platform-specific load: calls dlopen (POSIX) or LoadLibrary (Windows).
        /// On Windows, the DLL is first copied to m_temp_path to release the file lock.
        DLHandle PlatformLoad(const char* path);

        /// Platform-specific symbol resolution.
        void*    PlatformSym(DLHandle handle, const char* name);

        /// Platform-specific unload.
        void     PlatformUnload(DLHandle handle);

        /// Resolve all four ZGame_* symbols from handle into out_funcs.
        bool     ResolveFunctions(DLHandle handle, GameDLLFunctions& out_funcs);

        /// Generate a per-reload unique temp path to avoid stale-handle issues on Windows.
        void     MakeTempPath(const char* original_path, char* out_temp_path, uint32_t buf_size);

        DLHandle          m_handle    = nullptr;
        GameDLLFunctions  m_funcs     = {};

        // Windows: temp copy path. Empty on POSIX (dlopen does not lock the file).
        char m_temp_path[512] = {};
    };

}  // namespace ZEngine::Scripting
```

### Platform implementation notes

**POSIX (Linux / macOS):**

```cpp
DLHandle GameDLLLoader::PlatformLoad(const char* path) {
    // RTLD_NOW: resolve all symbols immediately; fail fast if a symbol is missing.
    // RTLD_LOCAL: do not export DLL symbols into the global namespace.
    //             This is critical when reloading: two copies of the DLL must not
    //             interfere with each other's static-init state.
    DLHandle handle = dlopen(path, RTLD_NOW | RTLD_LOCAL);
    if (!handle) {
        // dlerror() returns a human-readable error string.
        ZEngine::Log::Error("dlopen failed: {}", dlerror());
    }
    return handle;
}

void* GameDLLLoader::PlatformSym(DLHandle handle, const char* name) {
    // Clear any prior error, then resolve.
    dlerror();
    void* sym = dlsym(handle, name);
    const char* err = dlerror();
    if (err) {
        ZEngine::Log::Error("dlsym '{}' failed: {}", name, err);
        return nullptr;
    }
    return sym;
}

void GameDLLLoader::PlatformUnload(DLHandle handle) {
    dlclose(handle);
}
```

**Windows:**

```cpp
DLHandle GameDLLLoader::PlatformLoad(const char* path) {
    // Windows locks the DLL file while it is loaded.
    // Copy to a temp path first so the build system can overwrite the original.
    MakeTempPath(path, m_temp_path, sizeof(m_temp_path));
    if (!CopyFileA(path, m_temp_path, /*failIfExists=*/FALSE)) {
        ZEngine::Log::Error("CopyFile failed: {}", GetLastError());
        return nullptr;
    }
    DLHandle handle = LoadLibraryA(m_temp_path);
    if (!handle) {
        ZEngine::Log::Error("LoadLibrary failed: {}", GetLastError());
    }
    return handle;
}

void* GameDLLLoader::PlatformSym(DLHandle handle, const char* name) {
    void* sym = reinterpret_cast<void*>(GetProcAddress(handle, name));
    if (!sym) {
        ZEngine::Log::Error("GetProcAddress '{}' failed: {}", name, GetLastError());
    }
    return sym;
}

void GameDLLLoader::PlatformUnload(DLHandle handle) {
    FreeLibrary(handle);
    // Clean up temp copy.
    if (m_temp_path[0] != '\0') {
        DeleteFileA(m_temp_path);
        m_temp_path[0] = '\0';
    }
}
```

`MakeTempPath` appends a monotonically increasing counter to the filename stem:
```
game.dll → game_reload_0001.dll
           game_reload_0002.dll
           ...
```
Old temp copies are deleted by `PlatformUnload`.

### Hot-reload trigger via VFSFileWatcher

The engine's `VFSFileWatcher` (see `vfs-ticket4-filewatcher.md`) monitors the DLL path.
When a `Modified` event arrives, the engine calls `GameDLLLoader::Reload` on the next
frame boundary (not mid-frame):

```cpp
// ZEngine/Scripting/ScriptingSubsystem.cpp

void ScriptingSubsystem::Initialize(ZGameContext* ctx) {
    m_ctx = ctx;
    m_loader.Load(m_dll_path, ctx);

    // Register a file watcher on the DLL path.
    m_watcher_handle = m_ctx->VFS->WatchFile(
        VFSPath(m_dll_path),
        [this](VFSFileEvent event) {
            if (event == VFSFileEvent::Modified) {
                m_reload_pending = true;
            }
        });
}

void ScriptingSubsystem::BeginFrame() {
    if (m_reload_pending) {
        m_reload_pending = false;
        m_loader.Reload(m_dll_path, m_ctx, m_ctx->WorldTick, m_ctx->Scene);
    }
}
```

`m_reload_pending` is an `std::atomic<bool>` — the watcher callback fires from the VFS
watcher thread; `BeginFrame` is called from the main thread.

## 4. Hot-Reload Safety

Hot-reload works because ECS component data lives in the engine, not in the DLL. This
section documents exactly what survives a reload and what does not, so game programmers
do not create unsafe patterns.

### What survives a reload

| Data | Location | Survives reload? | Notes |
|---|---|---|---|
| ECS component data (`TransformComponent`, etc.) | `ECS::Scene` — engine | Yes | Never in the DLL |
| `EntityID` values | `ECS::EntityRegistry` — engine | Yes | Never in the DLL |
| Actor instances (`Ref<Actor>`) | `ActorManager` — engine | No (see below) | Vtable points into DLL |
| `AudioEngine` state | Engine | Yes | DLL only holds a pointer |
| `PhysicsWorld` rigid bodies | Engine | Yes | DLL only holds a pointer |
| DLL-local static variables | DLL `.bss` / `.data` | No | Destroyed on unload |
| DLL-local heap allocations | DLL heap (if CRT is shared) | Depends | See below |

CONSTRAINT: ECS components are plain data and must NOT store Ref<Actor> (or any
pointer into a game DLL type). Cross-entity actor references must be stored as
EntityID values, not as Ref<Actor> pointers. This is consistent with the
actor-ecs-architecture.md component ownership rules.

However, DLL-local globals and game-code variables (not ECS components) may
hold Ref<Actor>. These must be cleared before ActorManager::DestroyAllActors()
is called during reload. Failure to do so leaves Ref<Actor> objects alive whose
vtable points into the unloaded DLL — calling any virtual method after DLL
unload is undefined behavior.

Game code must release DLL-local actor references in Actor::OnDestroy():
    void MyActor::OnDestroy() override {
        // Clear any DLL-local Ref<Actor> (NOT ECS component fields)
        m_cached_target_actor = nullptr;   // DLL-local member, not a component
    }

To resolve a cross-entity actor reference at runtime, store the EntityID in a
plain-data component and call ActorManager::GetActor(entity_id) each time:

### ECS component data — safe

```
Reload sequence:
  ECS::Scene (engine)
    └── ComponentStorage<TransformComponent>  ← lives here, unaffected by DLL reload
    └── ComponentStorage<HealthComponent>     ← lives here, unaffected by DLL reload
    └── ...
```

ECS systems are function objects or lambdas registered into `WorldTick`. After reload, all
game systems are cleared via `WorldTick::BeginRebuild()` and re-registered via
`ZGame_RegisterSystems`. The component data remains intact.

### Actor instances — requires the Actor factory pattern (see Section 5)

`Actor` subclasses (`PlayerActor`, `EnemyActor`) are defined in the DLL. Their vtables
point into DLL code. After unloading the old DLL, those vtable pointers become dangling.

The safe approach: before unloading the old DLL, destroy all Actor instances managed by
`ActorManager`. After loading the new DLL, recreate them using the Actor factory
(see Section 5) by reading their `EntityID` and component data, which survived in the
`ECS::Scene`.

```
Before reload:
  ActorManager owns Ref<PlayerActor>
  PlayerActor::OnTick() vtable → old DLL code (valid)

After reload (naive):
  ActorManager still holds Ref<PlayerActor>
  PlayerActor::OnTick() vtable → UNLOADED DLL (crash)

After reload (correct, factory pattern):
  1. Engine calls ActorManager::PrepareReload()
     → collects {EntityID, actor_type_id} for all live Actors
     → calls OnDestroy() on each
     → drops all Ref<Actor> (refcount hits zero, ~Actor runs but does NOT call DestroyEntity)
  2. DLL unloads
  3. New DLL loads, registers factories
  4. Engine calls ActorManager::RestoreFromReload(saved_records)
     → calls factory for each actor_type_id
     → wraps the existing EntityID with the new Actor subclass
     → calls OnCreate() is NOT called (data already in components)

**OnDestroy timing during reload:**
`DestroyAllActors()` calls `OnDestroy` on each actor BEFORE the old DLL is unloaded.
This means `OnDestroy` can safely call any DLL function or game system.
After the old DLL is unloaded and the new DLL is loaded, `RestoreFromReload()` creates
new Actor instances via the factory registry. It does NOT call `OnCreate` — the actor
must initialize from its existing ECS component data (which was preserved across the reload).
Game code in `OnCreate` must be idempotent with respect to existing component state.
```

### Static state in the DLL — lost on reload

The game programmer must design game systems to be stateless with respect to the DLL.
All mutable state must live in ECS components, `ActorManager`-owned Actor instances, or
engine subsystems. A `static float s_timer = 0.0f;` in the DLL is reset to zero on reload.

If truly persistent DLL-side state is needed, store it in a dedicated ECS component
(e.g. `GameStateComponent` on a singleton entity) and read it back at the start of
`ZGame_Initialize`.

### CRT heap and memory — shared CRT is required

On Windows, both the engine and the game DLL must link against the same CRT DLL
(`msvcrt.dll` / `ucrtbase.dll`). This ensures that `malloc`/`free` calls in the DLL use
the same heap as the engine. If the game DLL links the CRT statically, heap allocations
made before a reload and freed after will corrupt memory.

ZEngine rule: both the engine and the game DLL must be built with `/MD` (dynamic CRT) on
Windows. This is enforced in `CMakeLists.txt` (see Section 10).

## 5. Actor Subclassing Across the DLL Boundary

### The problem

```
Actor base — defined in engine
  └── PlayerActor — defined in DLL
        OnTick() → DLL code
        OnCreate() → DLL code
```

When the DLL is unloaded, `PlayerActor`'s vtable becomes invalid. Any indirect call
through an existing `Ref<PlayerActor>` is undefined behavior.

### Solution: Actor factory pattern

The DLL registers **factory functions** for each Actor subclass at `ZGame_Initialize` time.
The engine's `ActorManager` stores these factories and uses them both for initial
creation and for post-reload recreation.

```cpp
// ZEngine/ECS/ActorManager.h (relevant excerpt)
namespace ZEngine::ECS {

    /// Unique ID for an Actor subclass. Stable across reloads (assigned by name hash).
    using ActorTypeID = uint32_t;

    /// Factory function: given an existing EntityID in scene, construct and return an Actor.
    using ActorFactory = Ref<Actor> (*)(Scene& scene, EntityID id);

    class ActorManager {
    public:
        // ...

        /// Register a factory for an Actor subclass.
        /// Called from ZGame_Initialize for each game Actor type.
        void RegisterActorFactory(ActorTypeID type_id, ActorFactory factory);

        /// Create a new Actor of the given type.
        /// Calls factory(scene, scene.CreateEntity()), then calls OnCreate().
        Ref<Actor> CreateActor(ActorTypeID type_id, Scene& scene);

        /// Wrap an existing EntityID with an Actor of the given type.
        /// Does NOT call OnCreate(). Used during post-reload restoration.
        Ref<Actor> WrapActor(ActorTypeID type_id, Scene& scene, EntityID id);

        /// Collect all live actor records in preparation for a reload.
        struct ActorRecord { EntityID ID; ActorTypeID TypeID; };
        void PrepareReload(Core::Containers::Array<ActorRecord>& out_records);

        /// Destroy all live Actors (calls OnDestroy, drops Ref).
        /// Entity data in Scene is preserved.
        void DestroyAllActors();

        /// Recreate actors from saved records after a reload.
        void RestoreFromReload(const Core::Containers::Array<ActorRecord>& records,
                               Scene& scene);
    };

}  // namespace ZEngine::ECS
```

### Game DLL side

```cpp
// Game/Actors/PlayerActor.h
class PlayerActor : public ZEngine::ECS::Actor {
public:
    static constexpr ZEngine::ECS::ActorTypeID TYPE_ID = 0xA1B2C3D4u; // deterministic hash

    void OnCreate() override {
        AddComponent<TransformComponent>({});
        AddComponent<PlayerInputComponent>({});
        AddComponent<CameraComponent>({});
    }

    void OnTick(float dt) override {
        auto* input = GetComponent<PlayerInputComponent>();
        // ... gameplay logic ...
    }
};

// Game/GameMain.cpp
void ZGame_Initialize(ZGameContext* ctx) {
    // Register factory: given a scene + EntityID, wrap it in a PlayerActor.
    ctx->ActorManager->RegisterActorFactory(
        PlayerActor::TYPE_ID,
        [](ZEngine::ECS::Scene& scene, ZEngine::ECS::EntityID id) -> Ref<Actor> {
            return Actor::Wrap<PlayerActor>(scene, id);
        });
    // ... register other actor types ...
}
```

`Actor::Wrap<T>` is a templated static factory in the engine that allocates a `T`
from the engine's persistent arena (not the DLL heap) and sets its `EntityID` and `Scene*`
without calling `OnCreate`.

### `ActorTypeID` assignment

`TYPE_ID` is a `constexpr uint32_t` — a FNV-1a hash of the type name string computed at
compile time. It is identical across reloads as long as the class name does not change.
Do not use `__COUNTER__` or `typeid` for this — both are reload-unstable.

## 6. System Registration Pattern

ECS systems in the game DLL are registered into `WorldTick` during `ZGame_RegisterSystems`.
The hot-reload protocol uses `WorldTick::BeginRebuild()` and `WorldTick::Commit()` to
safely rebuild the system DAG without disrupting in-flight frames.

### Registration on first load

```cpp
// Game/GameMain.cpp

void ZGame_RegisterSystems(ZEngine::ECS::WorldTick* world,
                           ZEngine::ECS::Scene*     scene)
{
    using namespace ZEngine::ECS;

    SystemID player_system_id = world->RegisterSystem(
        "PlayerMovementSystem",
        [](Scene& sc, float dt) {
            sc.ForEach<TransformComponent, PlayerInputComponent>(
                [dt](EntityID id, TransformComponent& t, PlayerInputComponent& inp) {
                    t.Position += inp.MoveDirection * inp.Speed * dt;
                });
        },
        SystemDescriptor{
            .ReadMask  = MaskBit(ComponentTypeOf<PlayerInputComponent>()),
            .WriteMask = MaskBit(ComponentTypeOf<TransformComponent>()),
        });

    SystemID ai_system_id = world->RegisterSystem(
        "NPCPatrolSystem",
        [](Scene& sc, float dt) {
            sc.ForEach<TransformComponent, NPCPatrolComponent>(
                [dt](EntityID id, TransformComponent& t, NPCPatrolComponent& npc) {
                    // Advance patrol path ...
                });
        },
        SystemDescriptor{
            .ReadMask  = MaskBit(ComponentTypeOf<NPCPatrolComponent>()),
            .WriteMask = MaskBit(ComponentTypeOf<TransformComponent>()),
        });

    // PlayerMovementSystem and NPCPatrolSystem both write TransformComponent — conflict.
    // Declare explicit ordering: player first, AI second.
    world->OrderBefore(player_system_id, ai_system_id);
}
```

### Hot-reload sequence for `WorldTick`

The `WorldTick::BeginRebuild()` / `Commit()` pair is modeled on a double-buffer:
`BeginRebuild()` marks the DAG as "under construction" and prevents any new tick from
dispatching; `Commit()` rebuilds the dependency graph and re-enables dispatch.

**BeginRebuild() blocking contract:** Sets the stop flag and waits for the current
wave to complete before returning. No system function executes after BeginRebuild()
returns. In-flight systems are NOT interrupted — they are allowed to finish their
current execution. The caller must not assume any partial state; all observable
side effects of in-flight systems will have completed before this function returns.

```cpp
// ZEngine/Scripting/GameDLLLoader.cpp (inside Reload)

bool GameDLLLoader::Reload(const char* dll_path,
                           ZGameContext* ctx,
                           ECS::WorldTick* world,
                           ECS::Scene* scene)
{
    // 1. Suspend the scheduler — no more ticks until Commit().
    world->BeginRebuild();

    // 2. Prepare actor record list (populated in Step 2b).
    Core::Containers::Array<ECS::ActorManager::ActorRecord> actor_records;

    // Step 2b — Drain all pending work before unloading the DLL.
    // Any deferred work that holds pointers to DLL code must complete first.
    // Order matters: audio first (may have pending callbacks), then async imports,
    // then actor destruction (calls OnDestroy which is DLL code).

    ctx->AudioEngine->Flush();              // drain all pending AudioCommand ring buffer
    ctx->ImportCoordinator->CancelAll();    // cancel in-flight async import jobs referencing DLL importers
    ctx->ActorManager->PrepareReload(actor_records); // collect entity IDs before destroying
    ctx->ActorManager->DestroyAllActors();  // calls Actor::OnDestroy (still safe: old DLL loaded)

    // Only NOW is it safe to call ZGame_Shutdown and unload the old DLL.

    // 3. Shutdown old game code.
    m_funcs.Shutdown();

    // 4. Unload old DLL.
    PlatformUnload(m_handle);
    m_handle = nullptr;

    // 5. Load new DLL.
    DLHandle new_handle = PlatformLoad(dll_path);
    if (!new_handle) {
        // Reload failed — we are now in a broken state.
        // In a shipping build this should never happen; log a fatal error.
        ZEngine::Log::Fatal("Reload failed: could not load new DLL '{}'", dll_path)
        return false;
    }

    GameDLLFunctions new_funcs{};
    if (!ResolveFunctions(new_handle, new_funcs)) {
        PlatformUnload(new_handle);
        // Log which specific symbol failed to help diagnose incomplete game DLL exports.
        if (!new_funcs.Initialize)     ZENGINE_CORE_CRITICAL("GameDLL: missing symbol ZGame_Initialize");
        if (!new_funcs.Shutdown)       ZENGINE_CORE_CRITICAL("GameDLL: missing symbol ZGame_Shutdown");
        if (!new_funcs.RegisterSystems) ZENGINE_CORE_CRITICAL("GameDLL: missing symbol ZGame_RegisterSystems");
        if (!new_funcs.OnSceneLoad)    ZENGINE_CORE_CRITICAL("GameDLL: missing symbol ZGame_OnSceneLoad");
        ZENGINE_VALIDATE_ASSERT(false, "GameDLL: one or more required symbols not exported. See CRITICAL log above.")
        return false;
    }

    // 6. Swap handles.
    m_handle = new_handle;
    m_funcs  = new_funcs;

    // 7. Initialize new game code.
    // Validate ZGameContext version before calling ZGame_Initialize
    ZENGINE_VALIDATE_ASSERT(m_funcs.Initialize != nullptr, "ZGame_Initialize not found");
    // Pass a temporary context to check version before full init
    ZGameContext version_check{};  // default-constructs with ContextVersion = ZGAME_CONTEXT_VERSION
    // Game DLL validates version in ZGame_Initialize via the context it receives
    m_funcs.Initialize(ctx);

    // 8. Re-register systems into the world (DAG is currently empty).
    m_funcs.RegisterSystems(world, scene);

    // 9. Rebuild the DAG and re-enable ticking.
    world->Commit();

    // 10. Restore actor instances using the new DLL's factories.
    ctx->ActorManager->RestoreFromReload(actor_records, *scene);

    ZEngine::Log::Info("Game DLL reloaded successfully.")
    return true;
}
```

**Design notes:**

- `BeginRebuild()` must be called before any DLL-supplied function pointers are
  invalidated. If a game system lambda captured a `this` pointer into the old DLL's
  heap, that pointer is dangling after step 4. `BeginRebuild()` ensures no system
  runs between steps 1 and 9.
- If `Reload` fails at step 5 or 6, the engine is in a degraded state: no game systems
  are registered and all Actor instances are gone. The engine continues running
  (rendering a scene with only ECS component data and no Actor behavior). The developer
  must fix the build error and trigger another reload.
- Steps 7–9 call the same functions that are called on first load. `ZGame_RegisterSystems`
  is not a special reload-time API; it is exactly the same function called at startup.

## 7. Lua Scripting (v2 Design)

This section is a brief forward-looking design for Lua scripting. It is not implemented
in v1. The DLL hot-reload system (v1) must be fully stable before Lua is added.

### Rationale

Lua is appropriate when:
- Designers (non-programmers) need to write behavior.
- Per-entity behavior varies significantly between entities (e.g. dialogue trees, quests).
- Full engine rebuilds even of the game DLL are too slow for the targeted iteration loop.

Lua 5.4 (MIT license) is the target. LuaJIT is not chosen because its ARM64 support is
incomplete and its update cadence has stalled.

### `LuaVM`

```cpp
// ZEngine/Scripting/LuaVM.h (v2 forward declaration)
namespace ZEngine::Scripting {

    class LuaVM {
    public:
        void Initialize(Core::Memory::ArenaAllocator* arena,
                        VFS::IVFSContext*             vfs);

        /// Load and compile a Lua script file. Returns a script handle.
        uint32_t LoadScript(const VFS::VFSPath& path);

        /// Execute the named global function in a specific script.
        void CallGlobal(uint32_t script_handle,
                        const char* func_name,
                        float dt);

        lua_State* GetRawState() { return m_L; }

        void Shutdown();

    private:
        lua_State* m_L = nullptr;
    };

}  // namespace ZEngine::Scripting
```

### `LuaScriptComponent`

```cpp
// ZEngine/ECS/Components/LuaScriptComponent.h (v2)
namespace ZEngine::ECS::Components {

    struct LuaScriptComponent {
        uint32_t  ScriptHandle;  // handle from LuaVM::LoadScript
        lua_State* Thread;       // coroutine per entity, avoids global-state collisions
    };

}  // namespace ZEngine::ECS::Components
```

### `LuaSystem`

```cpp
// v2 pseudocode
void LuaSystem(ECS::Scene& scene, float dt) {
    scene.ForEach<LuaScriptComponent>(
        [dt](EntityID id, LuaScriptComponent& sc) {
            // Resume the coroutine or call Update(dt) on the thread.
            lua_State* L = sc.Thread;
            lua_getglobal(L, "Update");
            lua_pushnumber(L, static_cast<double>(dt));
            if (lua_pcall(L, 1, 0, 0) != LUA_OK) {
                ZEngine::Log::Error("Lua error in entity {}: {}",
                                    id.Index, lua_tostring(L, -1));
                lua_pop(L, 1);
            }
        });
}
```

### Engine bindings

Bindings are hand-rolled C API functions registered into the Lua global table. `sol2` is
considered but its compile-time overhead is significant; hand-rolling is preferred for a
small, stable binding surface.

```lua
-- Example usage in a Lua script
function Update(dt)
    local t = entity:GetComponent("Transform")
    t.Position.X = t.Position.X + 100.0 * dt

    local hit = physics:Raycast(t.Position, Vec3(0, -1, 0), 5.0)
    if hit then
        entity:AddComponent("GroundedTag", {})
    end
end
```

### Hot-reload

When the VFS watcher reports `Modified` on a `.lua` file, the `LuaVM` reloads the file:

```cpp
lua_State* L = luaL_newstate();
luaL_openlibs(L);
int err = luaL_dofile(L, path);
if (err != LUA_OK) {
    ZEngine::Log::Error("Lua reload error: {}", lua_tostring(L, -1));
    lua_close(L);   // discard, keep old state
} else {
    lua_close(m_L); // discard old state
    m_L = L;        // swap
}
```

Per-entity coroutine threads (`LuaScriptComponent::Thread`) reference the old `lua_State`.
On reload, all coroutines must be recreated. This is simpler than Actor vtable restoration:
iterate all entities with `LuaScriptComponent`, create a new coroutine from the new
`lua_State`, and replace `Thread`.

## 8. Behavior Tree (v2 Design)

Behavior trees are the preferred architecture for NPC AI. This is a brief design for v2.

### Components

```cpp
// ZEngine/ECS/Components/BehaviorTreeComponent.h (v2)
namespace ZEngine::ECS::Components {

    enum class BTNodeStatus : uint8_t { Running, Success, Failure };

    struct BehaviorTreeState {
        uint32_t CurrentNodeIndex;  // index into the flat node array
        float    WaitTimer;         // used by Wait leaf node
    };

    struct BehaviorTreeComponent {
        uint32_t          TreeHandle;  // handle into BehaviorTreeLibrary
        BehaviorTreeState State;
    };

}  // namespace ZEngine::ECS::Components
```

### Node types

All nodes are stored in a flat array. Child indices are stored inline (no heap
pointer per node). This gives cache-friendly traversal with no virtual dispatch in
the hot path.

```cpp
// ZEngine/AI/BehaviorTree.h (v2, pseudocode)
enum class BTNodeType : uint8_t {
    Selector,    // try children left-to-right; succeed on first success
    Sequence,    // run children left-to-right; fail on first failure
    Condition,   // evaluate a predicate; return Success or Failure
    Action,      // execute an action; may return Running
    Wait,        // succeed after a fixed duration
};

struct BTNode {
    BTNodeType  Type;
    uint16_t    ChildCount;
    uint16_t    FirstChildIndex;  // index of first child in the flat array; 0 = leaf
    // For Condition/Action: function pointer or index into a registered callback table
    uint32_t    CallbackIndex;
};

struct BehaviorTree {
    Core::Containers::Array<BTNode> Nodes;
    uint32_t RootIndex = 0;
};
```

### `BehaviorTreeSystem`

```cpp
// v2 pseudocode
void BehaviorTreeSystem(ECS::Scene& scene, float dt) {
    scene.ForEach<BehaviorTreeComponent>(
        [&scene, dt](EntityID id, BehaviorTreeComponent& bt) {
            const BehaviorTree* tree = BehaviorTreeLibrary::Get(bt.TreeHandle);
            BTNodeStatus status = TickNode(tree, tree->RootIndex, id, scene, dt, bt.State);
            (void)status;  // root status ignored; tree runs every frame
        });
}
```

Nodes can be implemented as C++ lambdas (captured into the registered callback table)
or as Lua callbacks (v3). The flat array + index scheme avoids `std::function` overhead
in the hot path.

## 10. CMakeLists.txt

### Engine static library (excerpt)

The engine is built as a static library (or shared, if preferred). The game DLL links
against it.

```cmake
# ZEngine/CMakeLists.txt

add_library(ZEngine STATIC
    Scripting/GameDLLLoader.cpp
    Scripting/ScriptingSubsystem.cpp
    # ... other engine sources ...
)

target_include_directories(ZEngine PUBLIC
    ${CMAKE_CURRENT_SOURCE_DIR}          # allows #include <Scripting/GameAPI.h>
)

# C++20 everywhere.
target_compile_features(ZEngine PUBLIC cxx_std_20)

# Engine does not use exceptions or RTTI.
if (MSVC)
    target_compile_options(ZEngine PRIVATE /EHs-c- /GR-)
else()
    target_compile_options(ZEngine PRIVATE -fno-exceptions -fno-rtti)
endif()

# Windows: dynamic CRT is mandatory for shared heap with game DLL.
if (MSVC)
    target_compile_options(ZEngine PRIVATE /MD$<$<CONFIG:Debug>:d>)
endif()
```

### Game shared library

```cmake
# Game/CMakeLists.txt

add_library(ZEngineGame SHARED
    GameMain.cpp
    Actors/PlayerActor.cpp
    Actors/EnemyActor.cpp
    # ... other game sources ...
)

# Enforce dynamic CRT on Windows to match the engine's CRT linkage.
# Mixing /MT (static CRT) and /MD (dynamic CRT) causes heap corruption on DLL boundary.
# This check fires at configure time, not link time — failure is immediate and descriptive.
if(MSVC)
    get_target_property(_game_opts ZEngineGame COMPILE_OPTIONS)
    if(_game_opts MATCHES "/MT")
        message(FATAL_ERROR
            "ZEngineGame must use dynamic CRT (/MD or /MDd). "
            "Static CRT (/MT) causes heap corruption across the engine/game DLL boundary. "
            "Set CMAKE_MSVC_RUNTIME_LIBRARY to MultiThreadedDLL or MultiThreadedDebugDLL.")
    endif()
    set_property(TARGET ZEngineGame PROPERTY
        MSVC_RUNTIME_LIBRARY "MultiThreaded$<$<CONFIG:Debug>:Debug>DLL")
endif()

# Link against the engine.
target_link_libraries(ZEngineGame PRIVATE ZEngine)

# Include the engine's public headers (gives access to GameAPI.h, ECS/, etc.).
target_include_directories(ZEngineGame PRIVATE
    ${ZENGINE_INCLUDE_DIR}
)

target_compile_features(ZEngineGame PRIVATE cxx_std_20)

if (MSVC)
    # Windows: export all symbols (simplest approach for a game DLL).
    # The __declspec(dllexport) on extern "C" functions is sufficient; no /EXPORT linker flags needed.
    target_compile_options(ZEngineGame PRIVATE /MD$<$<CONFIG:Debug>:d>)

    # Generate a .pdb alongside the .dll for hot-reload debugging.
    target_link_options(ZEngineGame PRIVATE /DEBUG /PDB:$<TARGET_FILE_DIR:ZEngineGame>/ZEngineGame.pdb)
else()
    # POSIX: hide all symbols by default; only the four ZGame_* entry points are exported.
    target_compile_options(ZEngineGame PRIVATE
        -fno-exceptions
        -fno-rtti
        -fvisibility=hidden
    )
    # The four ZGame_* functions in GameMain.cpp must be annotated:
    #   __attribute__((visibility("default")))
    # This is already satisfied by extern "C" + the macro below.
endif()

# Convenience macro used in GameMain.cpp to mark exported symbols.
# Usage: ZGAME_EXPORT void ZGame_Initialize(ZGameContext* ctx) { ... }
# On POSIX: expands to __attribute__((visibility("default")))
# On Windows: expands to __declspec(dllexport)
target_compile_definitions(ZEngineGame PRIVATE
    $<IF:$<BOOL:${WIN32}>,ZGAME_EXPORT=__declspec(dllexport),ZGAME_EXPORT=__attribute__\(\(visibility\(\"default\"\)\)\)>
)

# Output the game DLL next to the engine executable for easy path resolution.
set_target_properties(ZEngineGame PROPERTIES
    RUNTIME_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/bin   # .dll on Windows
    LIBRARY_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/bin   # .so / .dylib on POSIX
)
```

### GameMain.cpp export annotation

```cpp
// Game/GameMain.cpp
#include <Scripting/GameAPI.h>
// ZGAME_EXPORT is defined by CMake (see above).

ZGAME_EXPORT void ZGame_Initialize(ZEngine::Scripting::ZGameContext* ctx) {
    // ...
}

ZGAME_EXPORT void ZGame_Shutdown() {
    // ...
}

ZGAME_EXPORT void ZGame_RegisterSystems(ZEngine::ECS::WorldTick* world,
                                        ZEngine::ECS::Scene*     scene) {
    // ...
}

ZGAME_EXPORT void ZGame_OnSceneLoad(ZEngine::ECS::Scene* scene) {
    // ...
}
```

**Design notes:**

- `ZGAME_EXPORT` is defined by the build system so `GameMain.cpp` compiles correctly on
  both platforms without `#ifdef _WIN32` in source.
- On Windows, `__declspec(dllexport)` on `extern "C"` functions produces undecorated
  names in the export table. `GetProcAddress("ZGame_Initialize")` resolves correctly.
- On POSIX, `-fvisibility=hidden` hides all symbols except those with
  `__attribute__((visibility("default")))`. This prevents symbol clashes when two copies
  of the DLL are loaded simultaneously during the reload transition window.
- The `.pdb` generation directive on Windows allows the debugger to attach to the running
  game even after a hot-reload, as long as the new `.pdb` is in the same directory as the
  new `.dll` copy.
- The game DLL must NOT link the engine as a shared library if the engine is built as a
  static library. Static library symbols must be resolved at game DLL link time, not at
  runtime. If both the engine executable and the game DLL link the engine statically, the
  engine's singleton instances (e.g. `RenderResourceManager::Get()`) will be duplicated.
  The correct build graph is: engine executable links engine static lib; game DLL links
  engine static lib; OR both link a shared engine lib. Choose one pattern and enforce it.
